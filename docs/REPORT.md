- **Connection/driver:** `lib/db.ts` uses the configured database connection; `lib/service-fee.ts` additionally imports `@vercel/postgres`. ORM usage is **not found**; application queries are parameterized raw SQL. The project has multiple database connection conventions, which is technical debt.
- **Schema tables:** initial tables and columns/types/foreign keys are defined in `scripts/01-init-schema.sql`: `users`, `businesses`, `password_reset_otps`, `categories`, `menu_items`, `addons`, `addon_options`, `menu_item_addons`, `drinks`, `popular_dishes`, `orders`, `order_items`, `transactions`, `withdrawals`, and `analytics`. Later migrations add/assume `refunds`, `transfer_recipients`, `admin_revenue`, `order_service_fees`, and related columns; their complete original definitions are **not found** in the initial schema and must be verified against the live Neon schema.
- **Initial constraints/relations:** primary keys are varchar IDs; unique constraints include `users.email`, `businesses.owner_id`, `businesses.slug`, and `analytics(business_id,date)`; foreign keys and delete actions are in `scripts/01-init-schema.sql`. Later `finance_records` has no declared foreign keys in `scripts/101_finance_settlement.sql`.
- **Indexes:** initial indexes are listed in `scripts/01-init-schema.sql`; finance indexes are in `scripts/052_finance_enhancements.sql` and `scripts/101_finance_settlement.sql`. Missing/uncertain indexes: `orders.payment_reference`, `orders.payment_status`, `orders.status`, `refunds.order_id`, `refunds.transaction_id`, and `finance_records.related_id` are not visibly indexed in the supplied SQL. Composite indexes for common `(business_id, payment_status, created_at)` queries are not found.
- **Money representation:** most money columns are `DECIMAL/NUMERIC(...,2)` in naira (`scripts/01-init-schema.sql`, `scripts/101_finance_settlement.sql`), while the legacy refund `amount` is explicitly kobo and `refund_amount` is naira (`app/api/refunds/request/route.ts`). This mixed-unit model is risky; money is not consistently stored as integer kobo. There are JavaScript `number` conversions and Paystack `*100` conversions (`app/api/payments/initialize/route.ts`, `app/api/business/withdrawals/route.ts`, `app/api/refunds/request/route.ts`).

IF NOT EXISTS` migrations (`scripts/01-init-schema.sql`, `scripts/052_finance_enhancements.sql`, `scripts/101_finance_settlement.sql`). ## 4. Money flow

- **Order total source:** the client submits `subtotal`, `serviceFee`, `deliveryFee`, and `total`; the order API persists submitted `total` as `orders.total_amount` and submitted `serviceFee` as `service_fee_amount` without server-side recomputation from menu/add-on prices (`app/api/orders/route.ts`). Service-fee calculation exists in `lib/service-fee.ts`: below ₦1,000 = ₦0; otherwise the highest matching tier is selected, and above ₦30,000 the formula is `tier.service_fee + floor((subtotal - 30,000) / 10,000) * 100`.
- **Items/add-ons:** `order_items.item_price`, quantity and JSONB configuration are accepted from the request; item price and add-on selections are not re-read and recomputed server-side (`app/api/orders/route.ts`). The schema stores `item_price` and `configuration` (`scripts/01-init-schema.sql`). Delivery-fee calculation is **not found** in the order API.
- **Paystack initialization:** `/api/payments/initialize` accepts client `amount`, order ID and email and passes the amount to Paystack (`app/api/payments/initialize/route.ts`, `lib/paystack.ts`). It does not visibly load the order total and compare it with the requested amount.
- **Successful payment:** webhook/verify settlement finds order by ID or payment reference, uses `orders.total_amount`, subtracts `service_fee_amount`, then inserts a transaction in the pending bucket and increments `businesses.pending_balance`; the formula is `netToBusiness = max(0, totalAmount - serviceFee)` (`app/api/payments/webhook/route.ts`, `app/api/payments/verify/route.ts`). It also increments total orders and menu item order counts. Admin revenue is credited with `serviceFee`, not a Paystack processing fee (`app/api/payments/webhook/route.ts`).
- **Webhook security/idempotency:** HMAC-SHA512 signature verification is implemented (`app/api/payments/webhook/route.ts`). The order status check prevents a second settlement after `payment_status` is paid/completed, but the transaction insert has no visible unique constraint on payment reference/order ID and is outside a database transaction. Errors inserting the transaction or balance update are caught and logged while the handler can still return success; concurrent webhook and verify requests can therefore race and potentially duplicate transaction/balance side effects.
- **Settlement:** daily cron finds `transactions` with pending settlement and due `available_at`, sums refunds, clamps transaction net to zero, subtracts aggregate from pending with `GREATEST(0, ...)`, adds to available, then marks rows settled (`app/api/cron/settle-balances/route.ts`). The intended timing is Mon–Thu next day 05:00 WAT and Fri–Sun Monday 05:00 WAT (`lib/wat.ts`, `scripts/101_finance_settlement.sql`). Balance update, row state update, and finance-record insert are not one database transaction; concurrent cron invocations are a race risk.
- **Withdrawals:** first three withdrawals per day are free; the fourth and later same-day requests add ₦500 (`app/api/business/withdrawals/route.ts`). Formula: `withdrawalFee = todayCount >= 3 ? 500 : 0`; `totalDeduction = amount + withdrawalFee`; amount is converted to kobo for Paystack with `round(amountNaira*100)` (`app/api/business/withdrawals/route.ts`). Available balance is checked, Paystack recipient and transfer are created, the withdrawal row is written, then balance is decremented. The count and deduction are not atomically locked, so parallel requests can bypass limits or overspend. Bank details are stored in transfer-recipient/withdrawal rows (`app/api/business/withdrawals/route.ts`, `scripts/052_finance_enhancements.sql`).
- **Reconciliation:** failed transfers can reverse gross amount plus withdrawal fee exactly once using `balance_reversed` (`lib/withdrawals.ts`, `scripts/101_finance_settlement.sql`), but the selected withdrawal GET query does not visibly select every field later inspected (`app/api/business/withdrawals/route.ts`), so the self-heal path needs live-schema/runtime testing.
- **Refunds:** owner authorization and paid status are checked; cumulative refunds cannot exceed order total. Refunds deduct from pending or available based on transaction bucket, but use `GREATEST(0, balance - refund)` rather than rejecting when the bucket is insufficient (`app/api/refunds/request/route.ts`). The formula is `remaining = orderTotal - sum(nonfailed/nonrejected refund_amount)` and accepted when `alreadyRefunded + refundAmount <= orderTotal`. The Paystack amount is `round(refundAmount*100)`. The requested Batch B rule to exclude service fee from refunds is **not implemented**; refund amount is compared to full order total and there is no service-fee subtraction in the refund calculation. Refund failure restores the bucket, but debit, refund row, Paystack call and reversal are not a single transaction/idempotency protocol. No refund webhook handler is found; retry/status handling is route-based (`app/api/refunds/[refundId]/route.ts`, `app/api/refunds/[refundId]/retry/route.ts`).
- **Paystack fee:** a calculated Paystack fee formula or persisted Paystack fee field is **not found**. The public policy mentions `1.5% + ₦100` (`app/refund-policy/page.tsx`), but application revenue logic credits the service fee (`app/api/payments/webhook/route.ts`).
- **Double-credit/double-debit risks:** webhook/verify concurrency; non-atomic balance and ledger updates; withdrawal count/balance race; refund balance clamp can hide an underfunded refund; settlement can be rerun between selecting rows and marking them; no visible uniqueness/idempotency constraints for provider references. Exact production impact is not determinable without live database and provider event data.

## 8. Specific checks

### a. “Some services are degraded” banner

The exact string and a matching health/degraded trigger are **not found** in the repository search. Therefore the trigger and whether it should be customer-visible are **not found**; do not infer it is tied to Paystack, SMS, or Better Uptime from the static code.

### b. “Order status mix” vs “Today”

`app/api/business/dashboard/order-status/route.ts` defaults to `range=30d`, and computes `intervalDays=29`, querying orders from the WAT date minus 29 days. Therefore “3 Pending (100%)” is a rolling 30-day-ish window, not necessarily today. The dashboard “Today” query is in `app/api/business/dashboard/route.ts`; the exact UI label wiring should be checked there, but the status-mix window is established by the cited route.

### c. Repeat rate

`app/api/business/dashboard/customer-metrics/route.ts` groups paid/completed orders by `customer_email`, counts customers with more than one order, and calculates `returning_customers / total_customers * 100`. Thus 7 customers all classified as returning produces 100%; it is lifetime per-business email repetition, not a time-window rate and not an identity-linked customer account metric.

### d. Pending orders June–September

Order status enum and payment status fields exist (`scripts/01-init-schema.sql`), but an expiry/cleanup/abandoned-order job is **not found**. The settlement cron handles paid transactions and withdrawal reconciliation, not unpaid order expiration (`app/api/cron/settle-balances/route.ts`). Pending rows can therefore remain unless another route changes them; a dedicated cleanup policy is **not found**.

## Recommended build order

1. **Financial correctness and data model first:** canonical integer-kobo ledger, provider event/idempotency tables, atomic balance mutations, refund/service-fee rules, and settlement/withdrawal state machines (`app/api/payments/*`, `app/api/refunds/*`, `app/api/business/withdrawals/route.ts`, `app/api/cron/settle-balances/route.ts`). This is highest risk because current flows accept client totals and perform multi-step non-transactional balance changes.
2. **Authorization and abuse controls:** central role/business scoping, customer identity model, rate limiting, OTP/PIN action policy, migration-route protection, request schemas, and safe logging (`middleware.ts`, `lib/auth.ts`, all mutation routes).
3. **Database migration/observability:** reconcile the live Neon schema with all SQL scripts, add missing foreign keys/unique constraints/indexes, and create auditable ledger/finance records before adding new payment providers.
4. **Foundation routing/auth:** implement host-based subdomain routing and correctly scoped shared cookies, then test all role redirects and tenant isolation (`middleware.ts`, `lib/auth.ts`).
5. **Customer foundation:** registration, account, addresses, order history, refund requests and wallet ledger; then Google sign-in only after account-linking rules are explicit.
6. **Restaurant operations:** Mapbox delivery areas, kitchen/table/POS workflows, offline outbox/replay protection, and OneSignal event delivery.
7. **UI system upgrade:** consolidate tokens/components, redesign dashboard/storefront/cart/checkout responsively, improve empty/error states and accessibility, and optimize image loading after the underlying data contracts stabilize.
8. **Growth analytics/features:** verified reviews, bundles, shareable/trending cart codes and analytics improvements, using consistent metric windows and event definitions.

**Audit limitation:** this is a repository/static audit. Live Neon constraints, actual Vercel cron schedules, provider dashboard settings, runtime logs, and production behavior are **not found** in source and should be verified before implementation decisions.
